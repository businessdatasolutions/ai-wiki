## [0:00] Why 10-minute AI agent demos fail in production

[0:00] In this video, you're going to learn the complete architecture of modern AI agent engineering straight from five Google engineers building these systems in production.
[0:10] Right now, most developers are stuck in a trap.
[0:13] It takes 10 minutes to build an AI agent demo that looks magical, but it's much harder to figure out why it hallucinated something,
[0:22] or why it deleted your unit test and submitted a massive broken pull request in production.
[0:29] Fixing that isn't just about writing better prompts.
[0:32] So let's explore the four layers of agent engineering with Logan, who will explain the four layers to us.
[0:41] Everything changing in AI engineering right now comes down to one shift, replacing yourself as the copy-paste middleman and moving from prompt engineering to loop engineering.

## [0:44] From prompt engineering to loop and harness engineering

[0:52] Loops live inside what we call the harness, the layer of software that sits between the raw models underneath, like Gemini or Gemma, and the finished application on top.
[1:00] It treats the model as a fixed black box and builds a system around it to make it reliable. When we look inside the harness, the engine at the center is simple.
[1:09] You take a model like Gemini, equip it with tools like a command line, file system access, or MCP servers, and wrap it in a while loop.
[1:17] That's the loop. On its own, a raw while loop is pretty brittle.
[1:21] To turn it into a system you can actually trust in production, you have to engineer the layers around it.
[1:26] Let's break down a production loop piece by piece across four layers, each one solving a specific mode of the engine.

## [1:33] Layer 1 (Learn): Context maps, persistent memory & modular skills

[1:33] Layer one is about managing the context window before the agent acts, and we can think about this in three parts.
[1:40] First, concise context maps.
[1:42] Instead of a massive manual that goes out of date, you give the loop a lightweight map, like an AGENTS file, that tells the agent how the repository is structured and where to look next.
[1:53] Second, persistent memory.
[1:55] On its own, the model forgets everything between runs, but we don't let that happen.
[1:59] For long tasks, the loop uses markdown plans and task lists on disk to record what is done, what failed, and what is next.
[2:08] Third, modular skills. Your agent doesn't need Cloud Run or IAM instructions on every run.
[2:14] Instead, you package specialized workflows and scripts into skills on disk that get pulled into the context window only when the loop actually needs them.
[2:22] That is how an agent learns new domain expertise on the fly without overloading the context window.
[2:28] Okay, so layer one gave our loop a map, a memory, and skills.
[2:33] The agent writes some code, runs the build tool, sees zero syntax errors, and stops the loop. Task complete, right?
[2:41] Not quite. Just because our code executed successfully doesn't mean it is doing what we want. That's why layer two wraps the loop in fast, deterministic guardrails.

## [2:45] Layer 2 (Guard): Fast, deterministic guardrails

[2:51] Now our code compiles, respects module boundaries, and passes every unit test in layer two. Are we ready to merge? Not quite.
[2:59] Code can pass 100% of your unit tests and still be wrong. Layer three adds semantic and multimodal review.

## [3:03] Layer 3 (Review): Decoupled semantic & multimodal critique

[3:06] Here, we decouple generation from critique.
[3:09] Instead of the coding agent grading its own homework, the harness spins up an independent reviewer agent, like Gemini, in a fresh, unbiased context window, to review the diff against your engineering standards.
[3:21] And because Gemini is natively multimodal, the loop can spin up the app in a headless browser, capture screenshots or video of the UI, and inspect how the feature actually looks and behaves before a human engineer gives final sign-off.
[3:34] With layers one, two, and three, we have a complete runtime engine for executing a single task. So what's layer four? Think about how an engine is built in the real world.

## [3:38] Layer 4 (Score): Evaluating and scoring the agent harness

[3:43] Layers one through three are the components inside the car while it's driving down the road. Layer four is the diagnostic test bench in the garage.
[3:51] Let's say you tweak your AGENTS file, add a new MCP tool, or upgrade models. Layer four is about evaluating and scoring the harness itself.
[4:00] Logan just gave us the blueprint for the entire four-layer engine. Learn, guard, review, and score.
[4:08] So let's dive deep into layer number one, learn.
[4:12] How can we get our agentic system to learn from a large amount of documents, rules, or tools?

## [4:13] Deep dive into Layer 1: How Agent Skills avoid context bloat

[4:19] If you add everything your agent needs to learn into the prompt, you end up killing your context window.
[4:26] That's exactly where agent skill comes in.
[4:29] Let's move over to Remik, who will teach us what agent skills are and how to use them.
[4:37] If you've ever tried to get an AI coding agent to follow your team's actual workflows, you've probably hit the same wall.
[4:45] Out of the box, coding agents rely on static training data, so they invent outdated SDK code, guess invalid CLI flags, or run risky terminal commands without asking.
[4:57] And if you try to fix that by stuffing 50 pages of rules and docs into your system prompt, you blow up your context window and make the agent even worse at coding.
[5:07] To fix this, you don't need a bigger model or a longer prompt. You need agent skills.
[5:13] Open-sourced in December 2025, the agent skills specification quickly became one of the biggest shifts
[5:20] in agent engineering, and today, it is supported across Claude Code, Codex, Antigravity, and almost every major coding harness.
[5:29] At its core, a skill isn't some complex framework. It is just a portable folder.

## [5:33] Anatomy of a Skill: SKILL.md, metadata, scripts & references

[5:35] Inside, you put a SKILL.md file with two things, a tiny metadata at the top describing when to use it, and the plain markdown instructions underneath explaining how to do the job.
[5:47] Plus, some optional folders for helper scripts or reference docs. Remember that scene in "The Matrix" where Trinity needs to fly a helicopter?
[5:56] She calls Tank and downloads the pilot program in seconds. That is what an agent skill feels.
[6:02] You package your workflow once, and a compatible agent can pick it up instantly.
[6:07] Now, the obvious question is, if I give my agent 100 skills, doesn't that still clog up the context window?

## [6:13] Progressive disclosure: Discovery, activation & execution stages

[6:15] No, and the reason why is progressive disclosure. Instead of dumping everything into memory at once, skills load in three stages.
[6:25] First stage, discovery.
[6:27] When your agent starts up, it only reads the short name and the description of each skill.
[6:32] That takes a minimum number of tokens, and it's just enough for an agent to know what's available. Second stage, activation.
[6:41] Only when your prompt actually matches a skill's description does the agent load the full SKILL.md file instructions into the memory.
[6:51] And three, the execution.
[6:53] Any extra files, reference files, or scripts are only loaded when this specific step is needed. So one skill travels fine on its own.
[7:02] If you just want your agent to format PRs or run a database migration your way, a single skill is all you need.
[7:09] Wrapping one skill in a plugin is an overkill.

## [7:11] Agent Plugins & the Google Cloud Developer Plugin (150+ skills)

[7:12] Where agent plugins actually earn their keep is when a complex domain needs multiple skills, live MCP servers, and routing rules working all together.
[7:22] Using a plugin.json manifest, you bundle all of these pieces into one installable unit.
[7:27] To wrap up, you don't have to choose between speed of AI coding agents and the safety of cloud best practices.
[7:34] With Google Cloud Developer plugin, you get one-click install, live documentation from Developer Knowledge MCP server,
[7:42] strict IAM and billing guardrails, and on-demand access to over 150 Google Cloud skills. And remember, it's not only limited to Antigravity.
[7:51] You can use the exact same plugin and skill catalog with Claude Code, Codex, or any other compatible agent.
[7:58] You can try it out today in under 30 seconds by opening Customizations in Antigravity, scrolling down to Build with Google,
[8:07] looking for the Google Cloud Developer plugin, and clicking Add.
[8:12] Now you know how to use agent skills when engineering your agentic system, so your agent can now learn.
[8:20] But there's something else. Let's say your AI agent gets stuck or is not able to carry out an action.

## [8:22] Deep dive into Layer 2: Why AI agents cheat & deterministic gates

[8:27] It might actually cheat.
[8:30] Prompting the model to be careful won't actually save you here, because a prompt is just advice.
[8:35] To keep bad code or bad actions from getting in the way of your agentic system, you need layer number two,
[8:43] which is cold, deterministic gates that the model cannot negotiate with or edit.
[8:50] Next up, we'll move on to Aron, who's going to teach us how to lock down your agentic system.
[8:57] When your agent finishes writing code and says all the tests passed, how can you trust it? Ask yourself three things.
[9:04] Were those tests already there, or did the agent just write them? Did it tweak any old tests just to get a green light?
[9:11] And if you ran those exact checks tomorrow on a totally fresh machine, would they still pass? If you don't know for sure, you're just taking the agent's word for it.
[9:20] Today, we're diving into deterministic checks, the hard rules that control what code your AI agent can actually keep.
[9:28] When I say deterministic check, I just mean running code that gives you the exact same result every time without any AI model chiming in or changing its mind.
[9:38] Compilers, type checkers, a test suite with fixed inputs, lint rules, secret scanners, source component analysis, and security tests based on defined rules.
[9:48] Why do these matter so much for agents? First, they're less expensive than using tokens and fast to run on every loop.
[9:54] Second, they give you clear feedback, like the exact file, line number, and error message.
[9:59] Prompt instructions or skills are great guidelines, but models don't always follow them perfectly.
[10:04] A hard deterministic gate is still a safety net to keep AI randomness more under control.
[10:10] Most people focus on security guardrails first, but security is a part of quality and overall stability.
[10:16] When an agent tries to rewrite half your codebase, ignores helper functions you already have, or breaks code that was working fine five minutes ago, you will feel the impact even if there are no security vulnerabilities.
[10:28] These are the gates that catch it. When writing new code, make sure new tests actually fail first. Otherwise, they're not really testing new functionality.

## [10:33] Enforcing Red-Green-Refactor & git hooks to stop test tampering

[10:37] Before writing implementation code, the harness runs the new test. If it passes right away, it's not testing anything new, so kick it back out.
[10:45] Moving in tiny red-green-refactor steps keeps commits small, so if something breaks, you know exactly what caused it.
[10:52] Agents can be sneaky when trying to get to green. They might change assertions, add skip tags, or disable linters. Don't just ask them nicely in the prompt.
[11:01] Set up actual Git hooks.
[11:03] Fail the run automatically if existing tests get edited, if test counts or coverage drop, or if config files get modified.
[11:12] Always rerun new tests a few times to catch flakiness. If a test only passes 80% of the time, block it until it's solid.
[11:19] Having tests clean up their own database state and run against a real local database helps keep things reliable.
[11:26] Security gates use the exact same idea: consistent inputs, predictable outputs, and clear error reports.
